# Reth v2.4.1 Dependency-Only Upgrade Design

## Summary

Upgrade Alethia Reth from its current pre-v2.3 Reth revision to the exact Reth
v2.4.1 release commit, `8eb210175687c9f0c889a3b6795c16781d830e3a`.
The change targets `main` and includes only the dependency alignment, source
migrations, and safety checks required for Reth v2.4.1.

JIT execution is deliberately deferred to a later pull request. This upgrade
must not add direct `revmc` dependencies, JIT feature wiring, JIT CLI or RPC
behavior, LLVM provisioning, or JIT-specific tests.

## Motivation

Reth v2.4.1 is a high-priority patch release for both payload builders and
non-payload builders. It updates Alloy core from 1.6.0 to 1.6.1. Alethia Reth
also needs the broader v2.1-to-v2.4 API migration because `main` currently pins
Reth commit `27bfddeada3953edc22759080a3659ccea62ca1f`.

Separating the dependency migration from JIT support keeps the first pull
request reviewable around compatibility and consensus preservation. The later
JIT pull request can then focus on execution-mode gating and compiler/runtime
behavior.

## Scope

The pull request will:

- Pin every direct `paradigmxyz/reth` git dependency to
  `8eb210175687c9f0c889a3b6795c16781d830e3a`.
- Align directly declared Alloy, Reth, revm, and Rust versions with Reth v2.4.1.
- Vendor the required `reth-optimism-trie` source and make it consume the same
  workspace Reth dependency set.
- Port Alethia Reth production code and tests to required v2.4.1 APIs.
- Preserve existing Taiko consensus, payload-building, RPC, proof-history, and
  execution behavior.
- Explicitly reject unsupported Amsterdam/BAL inputs instead of silently
  accepting newly introduced upstream fields.
- Regenerate `Cargo.lock` and verify that it contains one Reth git revision.

The pull request will not:

- Enable or expose Reth's `jit` feature.
- Add a direct `revmc` dependency.
- Add JIT execution wrappers, backends, helpers, controls, or tests.
- Install or configure LLVM in local builds, CI, or Docker.
- Refactor unrelated code or introduce unrelated behavior changes.

## Dependency Alignment

The workspace dependency set will follow Reth v2.4.1:

- Reth git crates:
  `8eb210175687c9f0c889a3b6795c16781d830e3a`
- Alloy API crates: `2.1.1`
- Alloy core crates (`alloy-primitives`, `alloy-sol-types`): `1.6.1`
- `alloy-evm`: `0.37.0`
- `alloy-rlp`: `0.3.16`
- Published Reth support crates (`reth-codecs`,
  `reth-primitives-traits`): manifest requirement `0.5.0`, resolving to
  `0.5.2` in the lockfile
- `revm-database-interface`: `41.0.0`
- Workspace MSRV and toolchain: Rust `1.95`

Reth's binary crate enables JIT by default in v2.4.1. Alethia Reth will consume
that crate with `default-features = false`, restore the existing non-JIT
feature set, and explicitly retain `reth-revm/portable`. This preserves current
runtime capabilities without introducing the LLVM dependency or JIT behavior.

## Optimism Trie Compatibility

The current Optimism dependency cannot be retained unchanged. Its
`reth-optimism-trie` package inherits a Reth revision from the Optimism
workspace, and that revision differs from the v2.4.1 release commit. Resolving
both revisions would introduce incompatible copies of Reth traits and types at
the proof-history boundary.

The pull request will therefore vendor `reth-optimism-trie` from Optimism
commit `4f21ce6b9574ffc3473dd3b622ec9f7bd0c72fad`, whose source was already
adapted to the v2.4-era APIs, into this repository. The vendored package will
inherit Alethia Reth's workspace dependencies so it resolves the same v2.4.1
Reth revision. The vendored directory will include a provenance document
recording:

- The upstream Optimism repository and source commit.
- The original package path.
- Any manifest-only adaptations made for workspace integration.
- The procedure for replacing or refreshing the vendored copy.

Vendored production code will remain otherwise source-equivalent to upstream.
Replacing the vendored copy with an Optimism git dependency is deferred until
Optimism publishes or pins a compatible Reth revision.

## Required API Migration

The migration will reuse the dependency-only lessons from the existing v2.4.0
work without bringing over its JIT implementation. Expected compatibility work
includes:

- Adapting consensus error construction to the new shared error shape.
- Updating block executor and executor-factory contracts, including associated
  types and transaction commit behavior.
- Delivering state hooks through the v2.4 state database interfaces.
- Passing the state-root handle through payload build arguments.
- Constructing built payloads from recovered blocks.
- Updating provider, storage, trie, engine, RPC, and CLI signatures where Reth
  changed trait bounds or data shapes.
- Threading new Amsterdam/BAL parameters through adapter boundaries while
  rejecting them wherever Taiko does not support the fork or fields.

Where an upstream API became infallible, Alethia Reth will preserve existing
failure semantics by validating fallible Taiko conditions before crossing the
infallible boundary. In particular, zk-gas block-budget checks must continue to
truncate or reject transactions at the same stage as before the upgrade.

## Safety Invariants

The implementation must preserve these invariants:

- Interpreter execution remains the only execution mode.
- Taiko fork selection and zk-gas metering do not change.
- Anchor transaction and base-fee-sharing behavior do not change.
- Unsupported Amsterdam/BAL fields fail closed.
- Proof-history reads and writes use one coherent set of Reth storage and trie
  types.
- Default and no-default-feature builds do not require LLVM.
- `Cargo.lock` resolves one `paradigmxyz/reth` source revision.

## Testing and Verification

Implementation will be verified with:

1. Targeted unit tests for each migrated boundary whose behavior or error
   handling changed.
2. Tests that unsupported Amsterdam/BAL inputs are rejected.
3. Existing proof-history and execution tests, including zk-gas truncation and
   anchor execution coverage.
4. `cargo check --locked --workspace --all-features`.
5. `cargo check --locked -p alethia-reth-bin --no-default-features`.
6. `just fmt`.
7. `just clippy`, including the repository's mandatory documentation gate.
8. `just test`.
9. A lockfile/source audit confirming a single Reth git revision and no direct
   JIT or `revmc` dependency.

If an all-features build activates JIT transitively, dependency features will
be corrected rather than adding LLVM to this pull request.

## Pull Request Structure

The implementation will live on `codex/reth-v2.4.1` and target `main`.
Commits should separate dependency and vendoring changes from source migration
and targeted correctness fixes where practical. The final pull request will
explain:

- Why the exact v2.4.1 commit is used.
- Why the Optimism trie is temporarily vendored.
- Which dependency families moved together.
- Which compatibility changes preserve existing Taiko behavior.
- That JIT support is explicitly deferred.
- The exact verification commands and results.

## Risks and Mitigations

- **Duplicate Reth type graphs:** prevented by vendoring the Optimism trie and
  auditing `Cargo.lock`.
- **Silent consensus drift:** mitigated with explicit invariants, targeted
  execution tests, and fail-closed Amsterdam handling.
- **Accidental JIT/LLVM coupling:** prevented by an explicit non-JIT feature
  list and a no-default-features build.
- **Large vendored diff:** constrained to an upstream snapshot with documented
  provenance and manifest-only workspace adaptations.
- **Migration omissions:** addressed by full workspace clippy and test runs,
  plus comparison against the already exercised v2.4.0 migration.

## Follow-Up

After this pull request is merged, a separate design and pull request may add
revmc JIT support on top of the stable v2.4.1 dependency baseline. That work
will own JIT feature flags, runtime gating, interpreter/JIT differential tests,
LLVM provisioning, and any JIT-specific CLI or RPC behavior.
