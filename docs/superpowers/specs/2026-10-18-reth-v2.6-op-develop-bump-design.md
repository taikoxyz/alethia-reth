# reth v2.6.0 bump pinned to OP develop: design

Date: 2026-10-18
Branch: `chore/bump-reth-v2.6.0` (worktree `.worktrees/chore-bump-reth-v2.6.0`, based on `origin/main` 99bbcf8)
Supersedes: taikoxyz/alethia-reth#241 (closed 2026-10-18; branch `origin/chore/bump-reth-v2.5.2`, head 8b7d1bd)

## 1. Intent

Alethia's proof-history feature depends on `reth-optimism-trie`, a git dependency on the OP monorepo
(`ethereum-optimism/optimism`, path `rust/op-reth/crates/trie`). That crate resolves reth inside OP's
workspace, so alethia's reth pin must be the byte-identical git URL + rev that OP uses, or cargo
builds two incompatible reth copies (CI guards this with `.github/scripts/check_reth_pin.sh`).

PR #241 bumped to reth v2.5.2 at OP `1cbf91ab`. OP develop has since moved on:

- ethereum-optimism/optimism#23067 (merged 2026-10-06) removed historical-proofs **v1** storage;
  #23328 (2026-10-13) keeps leftover v1 tables on disk but ignores them.
- #23046 (2026-10-16) moved OP to reth **v2.6.0**; #23471 (2026-10-16) moved the pin to
  `ethereum-optimism/reth@d9bd9875fe88dcc0183d78b187ce2ceab0c93e93` = v2.6.0 + backports of
  paradigmxyz/reth #27129, #27247, #27252, #27286, #27429, #27634, #27782, #27832 + CI commits.

`1cbf91ab` was the last OP commit with v2.5.2 + v1. Rather than land v2.5.2 and redo it, #241 was
closed and this PR goes straight to OP develop.

### Decisions already made by the owner (David)

1. Pin to OP develop (reth v2.6.0 fork `d9bd9875`); close #241 (done, with a comment) and carry its
   content forward.
2. Existing proof-history v1 data is **discarded**; storage is rebuilt in the v2 format.
3. Window initialization switches to **OP's v2 approach**: current-state initialization followed by a
   backward `BackfillJob` over reth's changesets ("option B"). This replaces alethia's own
   historical-anchor initialization + forward re-execution.
4. reth v2.6 state masking is **forced off** on every alethia node, the way op-reth does it.
5. Discarded v1 data is actually deleted from disk, not just ignored.

## 2. Goals, non-goals, anti-goals

Goals
- Workspace builds against OP develop + `ethereum-optimism/reth@d9bd9875` with a single reth source.
- No consensus change: block execution, assembly and state roots are byte-identical to main on all
  Taiko networks (verified by differential replay before merge).
- Proof-history nodes upgrade unattended: v1 storage is detected and deleted, v2 storage is built at
  startup, and `--proofs-history.backfill-window-only` nodes end up with the same retained window
  they have today in steady state: `[latest − window, latest]`, which is what the pruner keeps
  (upstream `resolve_prune_range` prunes below `latest − window`).
- No crash loop on any restart during the upgrade (mid-copy, mid-backfill, or after).
- State masking cannot be enabled.

Non-goals
- reth v2.7.0 (OP has no v2.7 bump yet).
- Running backfill concurrently with live indexing (see §5.4; possible follow-up).
- Snapshot-accelerated backfill (`run_with_snapshot`) (possible follow-up if hoodi timing is poor).
- Porting OP's `RethAuxiliaryProvider` execution source (not needed with masking 0; see §7).
- Fixing the reth#27252 all-zero `HashedAccounts` rows question (see §8).
- Changing the default (non-window-only) proof-history mode.

Anti-goals (would make this a failure even if it compiles)
- Production code silently opening a v1 directory as v2 and keeping the dead v1 tables forever.
  (The trap: `reth_optimism_trie::db::MdbxProofsStorage::new(&Path)` is the v1 store at `1cbf91ab`
  and the renamed v2 store at develop, same signature, so production code compiles unchanged.)
- Any block-hash / state-root divergence from main or taiko-geth.
- A proof-history node that crash-loops on upgrade, or that serves proofs from a half-built store.
- Losing the pre-Unzen SELFDESTRUCT correctness that #241 restored on the synchronous state-root path.

## 3. Constraints

- reth bumps are OP-first: every reth dependency line uses `https://github.com/ethereum-optimism/reth`
  rev `d9bd9875…`; `check_reth_pin.sh` must report a single source. If OP develop moves its reth pin
  again before this lands, stop and re-evaluate rather than chasing silently.
- The `reth-optimism-trie` rev is an OP develop commit that contains #23046 + #23471 and still pins
  `d9bd9875` (currently develop HEAD `9c14635375e22608458da1d3ec4830af491009dd`, 2026-10-16). The
  trie crate has not changed since `df7168efb5`; prefer the newest develop commit at implementation
  time that satisfies this.
- crates.io versions follow reth `d9bd9875`'s manifest: alloy 2.4.2, alloy-evm 0.39.0,
  alloy-hardforks 0.4.8, reth-codecs 0.7.0, reth-primitives-traits 0.7.1,
  revm-database-interface 43.0.0. Keep lock churn minimal (lockfile edits validated with
  `cargo metadata --locked`; `cargo update -p` can rewrite unrelated edges).
- Repo policy (`AGENTS.md`): every non-test production symbol documented; `just fmt`, `just clippy`,
  `just test` green; Conventional Commits ≤72 chars.
- This design doc (and any plan under `docs/superpowers/`) is removed from the branch before the PR
  is opened.

## 5. The changes

### 5.1 Carry-over from #241

Bring forward from `origin/chore/bump-reth-v2.5.2` (rebased onto main in the spike without conflicts):
- v2.5.x API adaptations: engine validator builder delegates to `BasicEngineValidatorBuilder::new(self)`;
  debug witness uses `ExecutionWitnessRecord::new(&state)`; live collector's fallible
  `hashed_post_state`.
- `check_reth_pin.sh` checking the full git source (URL + rev).
- `TaikoStateRootStrategy` (commit 8b7d1bd), re-adapted per §5.3.
- The `derived_block` wipe fix is **not** carried as-is (§5.2).
The history can be squashed; commit structure is the builder's call.

### 5.2 `derived_block.rs` without wipe markers

reth v2.6 deleted `HashedStorage::wiped`; destroyed storage is now expressed as explicit zero-valued
slots, which needs parent-state access (`reth_trie::hashed_cursor::zero_destroyed_account_storage`).
`execute_derived_block` only has a revm `Database`, so it cannot do that.

Decision (my call, flagged for review): drop the restoration loop in `hashed_post_state`, keep using
`HashedPostState::from_bundle_state`, and document on `DerivedBlockExecutionOutcome::hashed_state`
that storage of a destroyed pre-existing account is not conveyed (only reachable before Unzen, since
EIP-6780 limits SELFDESTRUCT to same-transaction-created accounts; every Taiko network is past Unzen).
Delete the two `wiped` tests. raiko2 must handle the same reth change when it bumps
(`crates/stateless/src/validation.rs:334`); note it in the PR body.

### 5.3 `TaikoStateRootStrategy` on v2.6

Bug status: still present at `d9bd9875`, v2.7.0 and reth main `e667968` (2026-10-17). With no
hashed-state receiver the validator's lazy hashed state is raw `HashedPostState::from_bundle_state`
(`crates/engine/tree/src/tree/payload_validator.rs:760-774`) and `SynchronousStateRootJob` roots it
(`state_root_strategy/mod.rs:994`), so pre-EIP-6780 destroy(+recreate) of an account with parent
storage yields a wrong root on the synchronous path (`--engine.state-root-fallback` or fewer than 5
available threads). None of the 8 backports touch this. The sparse path stays self-healing.

Unchanged APIs at `d9bd9875`: `BasicEngineValidator::with_state_root_strategy`, the
`StateRootStrategy` trait, `PreparedStateRootJob::new`, `StateRootJobOutcome::{new, with_hashed_state}`,
`DefaultStateRootStrategy::prepare` mode order (skip → synchronous → sparse),
`TreeConfig::use_state_root_task` (threshold still 5 threads).

Re-adaptation: the job context no longer exposes a provider (it holds a private
`OverlayStateProviderFactory<P, N>`), so the strategy owns its own `P` and `OverlayManager`, both
available in `build_tree_validator` (`ctx.node.provider().clone()`, `overlay_manager.clone()`; the
manager is `Clone` with shared state and is the same instance the tree uses). In `prepare`, when the
synchronous mode applies, build
`OverlayStateProviderFactory::new(provider, overlay_manager.overlay_builder(parent_hash))` and return a
synchronous job whose `finish` opens `database_provider_ro()` and computes the root from the
provider's `hashed_post_state` (which zeroes parent slots of destroyed pre-existing accounts) →
`state_root_with_updates` → `with_hashed_state(Some(..))`. This mirrors upstream's own
`compute_serial` (`mod.rs:1053-1064`) and `payload_validator.rs:1425-1438`.

Tests: keep the behavioural tests (sync path computes the correct root for destroy and
destroy+recreate over a test DB; routing picks the override only in synchronous mode). Delete the
"tripwire" tests: they exercise raw `from_bundle_state`, not reth's job, so they cannot detect an
upstream fix; `StateRootJobContext::new` is `pub(crate)`, so a true tripwire is impossible. Instead,
the module doc says to re-check `payload_validator.rs` on every reth bump.

### 5.4 Proof-history storage: v1 → v2

At open (`crates/node/src/proof_history/mod.rs`, `install_proof_history`):
1. Open `MdbxProofsStorage::new(&storage_path)`.
2. If `holds_only_legacy_v1_data()` is true: log a warning (path, that v1 data is being discarded),
   drop the handle, `remove_dir_all(storage_path)`, and reopen. Any I/O error aborts startup with an
   actionable message. Deleting the directory also removes the old historical-init metadata file
   (`taiko-historical-init-target`), which lives inside it.
3. A directory holding both v1 and v2 data cannot be produced by alethia (it never wrote v2); treat it
   like v2 (open as-is; upstream logs the leftover-table warning).
4. If the v2 store holds an **incomplete current-state initialization** (an initial-state anchor
   exists but no proof window has been committed, i.e. `get_earliest_block()` is `NoBlocksFound` and
   the init anchor status is not `NotStarted`), also log, delete the directory and reopen, so
   initialization restarts from scratch. Reason: upstream `InitializationJob::run` only resumes an
   `InProgress` anchor equal to the current best block and otherwise returns
   `InitializeStorageInconsistentState`; OP runs it offline, but alethia runs it inside a live node
   whose persisted tip keeps moving, so a restart mid-copy would crash-loop. Nothing was ever served
   from such a store (readiness is set only after initialization), so wiping it is safe. This check
   runs at open time, before any other handle to the store exists.

Remove `migrate_legacy_proof_history_storage` (it cannot trigger on v2: `commit_initial_state` writes
both Earliest and Latest) and its tests.

### 5.5 Proof-history initialization (option B)

Today (`sidecar.rs` `initialize_or_wait`, `storage_init.rs`):
- Default mode: current-state init at the on-disk best block, then grow forward.
- `--proofs-history.backfill-window-only`: window start = `finalized − window`
  (`proof_history_window_start_block`). WaitForFinalized / WaitForExecution wait; Ready → current-state
  init; MissedStart → historical-anchor init at the window start from in-memory reverse changesets,
  then the sync loop forward re-executes up to the executed head. A metadata file pins an interrupted
  historical init.

New behaviour:
- **Current-state init** uses upstream `reth_optimism_trie::InitializationJob::new(storage, tx,
  layout).run(best_number, best_hash)` (layout `Packed` when the node's storage settings are v2, else
  `Legacy`), against the raw `Arc<MdbxProofsStorage>` (no metrics wrapper, as OP's CLI does: the
  metrics layer accumulates per-observation memory during bulk init). `best_number`/`best_hash` must be
  read from the same reth read transaction handed to the job; the job refuses with
  `InitializeSourceTipMoved` otherwise, and with `InitializeSourceStateTrieUnwindPending` while a reth
  partial-trie unwind is pending. Alethia's `ProofHistoryInitializationJob` (`init.rs`) is deleted.
- **Window-only mode**: the start gates are unchanged — WaitForFinalized and WaitForExecution still
  wait (`finalized − window` is only used to decide *when* initialization may start, so a node that
  is still far behind does not initialize early and then forward-execute its whole sync). Ready and
  MissedStart both become: current-state init at the on-disk best block `B`, then backfill down to
  `B − window` (saturating), the same target rule as OP's `op-reth proofs init`. The resulting window
  `[B − window, B]` is exactly what the pruner keeps, so the startup prune check and the pruner never
  fight the backfill.
- **Backfill** uses upstream `BackfillJob::new(provider, storage).run(target)` (plain path, default
  batch size 25), where `provider` is a reth `database_provider_ro()` with
  `disable_long_read_transaction_safety()`. To avoid one reth read transaction pinning MDBX pages for
  the whole window (a long pinned reader also stalls reth's unwind on reorg), run it in chunks: each
  chunk opens a fresh provider and calls `run(max(target, earliest − CHUNK))`; `BackfillJob` resumes
  from the store's current earliest. No shutdown hook is needed: each batch commits atomically, so
  a killed backfill resumes from the last committed earliest. Chunk size is the builder's call
  (start around 10 000 blocks). Each block's diff is validated against the reth header state root
  by the job itself (`BackfillError::StateRootMismatch`); missing reth changesets surface as
  `BackfillError::BlockBodyPruned`.
- **Sequencing**: backfill runs as part of initialization, before readiness is set and before the
  sync and pruner tasks start (same position historical init has today). After it finishes, the
  existing sync loop forward-executes from the init block to the executed head, then live
  notifications take over. While it runs, proof RPCs behave as today when not ready: requests within
  1024 blocks of the tip fall back to canonical state, deeper requests error.
- **Resume**: the store's earliest block is the progress marker. In window-only mode, after
  reconciliation decides the store is usable (Ready / UnwindToEarliest), if
  `earliest > latest_stored − window` (saturating) the sidecar backfills down to
  `latest_stored − window` before the startup prune check and before setting readiness. This covers a
  restart in the middle of a backfill and an operator raising `--proofs-history.window`; in steady
  state the pruner keeps `earliest == latest − window`, so the rule is a no-op. The target is anchored
  on `latest_stored`, not on `earliest`, so retries converge (OP's CLI does the same). An interrupted
  current-state copy is handled by the wipe-at-open rule (§5.4 item 4). The historical-init metadata
  file and its helpers are deleted.
- **Errors**: a backfill or init error propagates out of the sidecar like other sidecar errors today
  (the node stops with the error). Messages for `StateRootMismatch` and `BlockBodyPruned` must say what
  the operator should do (wipe proofs storage / do not prune changesets inside the window).
- Removed: `HistoricalAnchorOverlay`, `run_historical_with_adapter`,
  `initialize_historical_proof_history_storage`, `PROOF_HISTORY_REVERT_SPAN_WARN_BLOCKS`,
  `ProofHistoryInitializationAction::HistoricalWindow`, historical-init metadata
  (`HistoricalInitMetadata` + read/write/validate/remove), `historical_init_resume_action`, and their
  tests. `--proofs-history.backfill-window-only` keeps its name; its help text is updated to describe
  the backward backfill.
- Unchanged: reconciliation (`proof_history_startup_action`), the startup prune safety check, the sync
  loop and live collector, the pruner, RPC overrides, readiness semantics, default mode.

### 5.6 State masking forced off

Mirror the two load-bearing parts of op-reth (`rust/op-reth/crates/cli/src/lib.rs:186-188`,
`crates/node/src/node.rs:401-411`); the op-reth help-hiding and post-parse clap error are left out
to keep the CLI parse path unchanged (owner's "keep it lean" principle, 2026-10-18):
- Before clap parses (`TaikoCli::parse_args` / `try_parse_args_from`, and the same two functions on
  `TaikoNodeCommand`), call `DefaultEngineValues::default().with_num_state_masking_blocks(0).try_init()`,
  so the flag defaults to 0 (and `--help` shows 0).
- At launch (`TaikoNodeCommand::execute`), fail with a clear error if the effective value (command line
  or `RETH_ENGINE_NUM_STATE_MASKING_BLOCKS`) is nonzero; an explicit 0 is accepted.
Applies to every alethia node, proof-history or not. This also keeps the existing k8s engine flags
(`--engine.persistence-threshold 128 --engine.memory-block-buffer-target 128`) valid; v2.6's startup
check `masking + buffer < threshold` only applies when masking is nonzero.

### 5.7 Mechanical fixes

- Assembler: compute the receipts root with
  `alloy_consensus::proofs::calculate_receipt_root(&receipts.iter().map(TxReceipt::with_bloom_ref).collect::<Vec<_>>())`
  (what reth's `EthBlockAssembler` does). The root must stay byte-identical; covered by existing
  assembler tests plus differential replay.
- CLI `Download`: `async move { command.execute::<TaikoNode>().await.map(|_| ()) }`.

## 6. Verification

Gates: `just fmt`, `just clippy`, `just test`, `check_reth_pin.sh`, `cargo metadata --locked`.

New or changed tests (one per rule, per the owner's preference for focused PRs):
- v1-only storage directory is deleted and reopened as an empty v2 store (build a v1 directory by
  creating the legacy tables directly; the trie crate's own legacy-table tests show how).
- Window-only initialization against a real temp `MdbxProofsStorage` and a test provider factory with
  real changesets over a few blocks (including a block that destroys a pre-existing account's storage
  and one that only creates storage): after init + backfill, the window bounds are `[B − window, B]`
  and `eth_getProof`-equivalent reads at earliest and at a middle block verify against the header
  state roots. A second test interrupts after one chunk and checks resume.
  (`InMemoryProofsStorage` must not be the only backend: it hid the append-order failure.)
- An incomplete current-state initialization found at open is wiped and initialization restarts.
- Masking: parsing `node` yields 0 by default; the launch check accepts 0 and rejects nonzero.
- `TaikoStateRootStrategy`: adapted behavioural + routing tests (§5.3).
- `derived_block`: wipe tests removed, doc updated (§5.2).

Pre-merge checks (outside CI):
- Differential replay of hoodi and mainnet block ranges: block hashes and state roots identical to main.
- Hoodi proof-history upgrade run: v1 directory deleted, init + backfill duration and disk recorded for
  the configured window, proofs served afterwards. Record numbers in the PR body.

## 7. Things already checked and found not to need changes

- OP #23046's switch away from reth's parent-state provider for proofs execution: alethia's live
  collector reads through `state_by_block_hash(parent)`; OP's failure needs the parent above the
  partial-state-trie frontier, which cannot happen with masking 0 (sync targets Finish; notification
  execution handles near-tip canonical blocks; pipeline sync leaves the in-memory chain empty).
- OP's abandoned-fork handling and ExEx durable-trie gate (the gate was removed before merge).
- Trie crate API used by live/sidecar/RPC code: unchanged apart from the v1 removal.
- Reorg/unwind boundaries in the v2 store behave like v1.

## 8. Risks and open questions (not blocking)

- reth#27252: before this pin, the engine's state-root task could persist EIP-161-emptied accounts as
  all-zero `HashedAccounts` rows; current-state init copies reth's tables verbatim, so such rows would
  be copied too. Whether Taiko DBs contain them is unknown. Out of scope; note in the PR body.
- Pruned nodes: v2.6 bytecode/BLOCKHASH reads below the history prune checkpoint fail
  (`InsufficientChangesets` / `StateAtBlockPruned`). Taiko-operated proof-history nodes do not prune;
  document that proof-history requires unpruned changesets for the window.
- Pre-existing: any sidecar error stops the node (`mod.rs` panics on sidecar error).

## 9. Operator-facing changes (for the PR body)

- Proof-history: v1 storage is deleted on first start and rebuilt as v2 (time and disk to be measured
  on hoodi); window-only nodes now fill the window backward from reth changesets instead of
  re-executing it.
- State masking is off and cannot be enabled; the flag is hidden.
- reth v2.6.0 defaults: `--engine.persistence-threshold` 7 → 50 (k8s sets 128 explicitly);
  `--rpc-cache.max-cached-tx-hashes` 30 000 → 100 000; `--rpc-cache.max-headers` is a hidden no-op;
  default `eth` wire version eth/69 → eth/71 (negotiated); `--txpool.minimum-priority-fee` now also
  applies to local transactions; `eth_getLogs` returns errors for pruned ranges and for `fromBlock`
  beyond head; `--txpool.max-batch-size 0` rejected; per-peer announced-hash limit 4096.
- Flags removed in reth v2.5 (`--engine.sparse-trie-max-hot-{slots,accounts}`) must be absent from
  deployment configs (carried from #241's checklist).
